# Changelog

## [0.4.0rc1]

### New Features

- **GUI raw-data & result viewers on the map** (`app/routes/render.py`, `app/frontend/src/JobQueueDrawer.tsx`, `Map.tsx`) — the **Downloader** panel's **View Data** button previews the raw downloaded scenes under `slc/` using each product's built-in georeferenced quicklook: Sentinel-1 SLC/burst overlay `preview/quick-look.png` at the 4 ground corners from `map-overlay.kml` (a rotated overlay), and NISAR GSLC shows a downsampled amplitude cached under `slc/.preview_cache/` (`/api/folder-slc-list`, `/api/render-slc-preview`). The **Processor** panel's viewer is renamed **View Result** and now renders geocoded interferograms from **all** local processors — HyP3 (zipped GeoTIFFs), ISCE3 (`unwrapped/`, `interferograms/` GeoTIFFs) and GMTSAR (`*_ll.grd`), not just HyP3 (`/api/folder-ifg-list` + `/api/render-tif` gained loose-file and `.grd` support). The map overlay now supports a 4-corner quad (`RasterOverlay.corners`) so tilted S1 quicklooks are placed correctly.

- **Adaptive coherence thresholds in the MintPy analyzers** (`analyzer/mintpy_base.py`) — `network.minCoherence`, `networkInversion.maskThreshold` and `reference.minCoherence` default to `"adaptive"`, resolved during `prep_data` from the stack's actual coherence distribution: `minCoherence` = strictest threshold keeping the network connected+redundant (cap 0.6), `maskThreshold` = reliable-fraction percentile (cap 0.6), `reference.minCoherence` = 98th percentile, min 0.30 (cap 0.85). Adaptation only kicks in below the cap; a clean stack gets the cap. Set an explicit number to override.

- **`ISCE3_Dolphin_PL` now serves both ISCE3 processors** (`analyzer/dolphin_sbas.py`, `core/base.py`, frontend) — its `compatible_processor` became a tuple `("ISCE3_Burst", "ISCE3_NISAR")`, so the time-series analyzer appears in the GUI dropdown (and the CLI tree) for a NISAR workdir too. The registry matcher and the frontend filter now accept a list of compatible processors.

- **Analyzer `run()`/`--container`/HPC symmetry** (`analyzer/mintpy_base.py`, `cli/main.py`) — `analyzer.run()` now routes to `submit_hpc()` when `hpc_mode` is set (mirroring `processor.submit()`), so the API is uniform. The CLI `run` subparser gained `--container` in its canonical position (after the action); a bare `--container` resolves to the analyzer's default image.

- **`ISCE3_NISAR` AOI `crop` is now an explicit stage** (`processor/isce3_nisar.py`) — the GSLC→AOI windowing is a first-class stage (`crop`, `ifg`, `stitch`, `unwrap`), so it shows in `refresh` and can be submitted/inspected on its own.

- **Processor (`ISCE3_NISAR`)** — a new local/HPC processor building an interferogram stack from **NISAR L2 GSLC** granules via [dolphin](https://github.com/isce-framework/dolphin) (feeds the `ISCE3_Dolphin_PL` analyzer). GSLC is already geocoded, so it shares `ISCE3_Burst`'s dolphin engine but skips the whole COMPASS front-end (`dem`/`tec`/`cslc`/`static`); stages are just `ifg`, `stitch`, `unwrap`, with `ifg` a single `wrapped_phase.run` over the stack (one frame per date, no burst split). Pair it with the `NISAR_GSLC` downloader. See [`docs/advanced/processor.md`](docs/advanced/processor.md).

- **`ISCE3_NISAR` crops each GSLC to the AOI before phase-linking** (`processor/isce3_nisar.py`) — a NISAR GSLC frame is enormous (e.g. 69840 × 68688 px) but the AOI is usually a small window. `ISCE3_Burst` gets its AOI cut for free from COMPASS's geocode `--bbox`; `ISCE3_NISAR` has no geocode step, so it windows each GSLC's complex-SLC subdataset to `AOI` into a cached VRT (`gdal_translate -of VRT -projwin`, `workdir/cropped_gslc/`) and dolphin phase-links only that window. Without it dolphin processes the full frame and the `stitch` `gdal_merge` OOMs on full-frame rasters (the AOI is otherwise only applied as a final output clip). On a real stack: 69840 × 68688 → ~8953 × 8728 per input (~60× smaller), a ~12 GB memory spike down to a few hundred MB. `process_full_extent` disables the crop.

- **NISAR downloaders (`NISAR_GSLC` / `NISAR_RSLC` / `NISAR_GUNW`)** documented in [`docs/advanced/downloader.md`](docs/advanced/downloader.md) — L2 GSLC (geocoded SLC → `ISCE3_NISAR`), L1 RSLC (radar SLC), and L2 GUNW (geocoded unwrapped interferograms). All extend `ASF_Base_Downloader` with NISAR's per-frequency-band polarization facets (`mainBandPolarization`/`sideBandPolarization`, `rangeBandwidth`); no orbit download (NISAR carries its own state vectors).

### Bug Fixes

- **ISCE2 `stackSentinel` steps silently orphaned by a trailing `&` (false `SUCCEEDED`)** (`processor/isce2_base.py`) — `_fix_cmd`, which resolves bare topsStack/ISCE `.py` script names to full paths and prepends `sys.executable`, preserved the trailing `&` that stackSentinel's `run_files` use for shell-level parallelism (`cmd &` … `wait`). But InSARHub runs each run-file line via `subprocess.run(shell=True)` inside its own thread pool, so a trailing `&` backgrounds the real work, the shell returns `rc=0` immediately, the step is marked `SUCCEEDED`, and the actual command is orphaned/killed when the wrapper exits. This produced empty unpacks and cascading `IndexError`/`AttributeError` failures many steps later (e.g. `invertMisreg.py` at run_08). `_fix_cmd` now strips a trailing `&`, so every command runs to completion under the pool's own concurrency. Fixed the whole 16-step ISCE2 chain that had been failing mid-run.

- **GMTSAR stack mode failed inside a container with `docker not found`** (`processor/gmtsar_s1.py`) — once `container` began being persisted to `insarhub_config.json`, the container child re-read it and `_stage_commands` wrapped each stack-stage command in **another** `docker run` (docker-in-docker), which the docker-less image can't do. `_stage_commands` now guards the wrap on `not INSARHUB_CONTAINER_CHILD`, so it still wraps for HPC child jobs (submitted from the host) but runs directly inside the local-container child. P2P mode never hit this (it doesn't generate run-files).

- **Analyzers hit the same container-in-container / premature-teardown bugs as the processors** (`analyzer/mintpy_base.py`, `analyzer/gmtsar_sbas.py`, `analyzer/dolphin_sbas.py`) — `run()`/`prep_data()`/`plot()` guarded container re-invocation only on `config.container`, not `INSARHUB_CONTAINER_CHILD`, so a containerized analyzer re-launched `docker run` inside the image. Added the `and not os.environ.get("INSARHUB_CONTAINER_CHILD")` guard (matching the processors), so the container-side runs MintPy/dolphin directly and synchronously.

- **GUI analyzer `prep_data` wrote an all-`auto` `.mintpy.cfg` in container mode** (`app/routes/analyzer.py`) — the per-step GUI route ran `prep_data()` inside the container (which resolves `mintpy.load.*` from the interferogram stack and writes the resolved `.mintpy.cfg`), then called `analyzer.config.write_mintpy_config()` again on the **host**, where the config was still `auto` — clobbering the container's resolved file. The three host-side `write_mintpy_config` sites are now skipped when `container` is set, so the container's resolved config survives. This shared route serves all three MintPy analyzers (`ISCE2_/Hyp3_/GMTSAR_Mintpy_SBAS`), so one fix covers all.

- **MintPy `quick_overview` crashed on a clean stack (`bins must be positive, when an integer`)** (`analyzer/mintpy_base.py`) — `quick_overview` runs `unwrap_error_phase_closure --action calculate`, which after writing `numTriNonzeroIntAmbiguity.h5` calls MintPy's histogram plotter with `bins = int(np.nanmax(data))`. When every pixel has zero non-zero-ambiguity triplets — i.e. the unwrapping was perfect, common for a small high-quality GMTSAR stack — `bins == 0` and numpy raises, aborting the whole run even though the `.h5` was already written. A small idempotent monkey-patch makes the plotter a no-op when `vmax <= 0`.

- **MintPy `correct_troposphere` crashed with `No module named 'pkg_resources'`** (`pyproject.toml`) — `pyaps3` (MintPy's tropo backend) still imports `pkg_resources` at runtime, which setuptools removed in v81; a fresh environment got setuptools ≥81 and the step died. Pinned `setuptools<81` in the project dependencies so `pkg_resources` is present again (drop once pyaps3 stops importing it).

- **`processor.refresh()` raised "No jobs loaded" right after a container/background submit** (`processor/isce2_base.py`) — when `submit()` runs in the background or inside a container, staging (and the job list) happens in the worker, so the host object's `self.jobs` is empty even though the run is live. `refresh()` now falls back to loading `<isce_dir>/isce_jobs.json` when `self.jobs` is empty (the CLI/GUI, which pre-load a saved job file, are unaffected).

- **`ISCE3_NISAR`/`ISCE3_Burst`/`GMTSAR` "View Result" showed nothing** (`app/routes/render.py`) — the viewer scanned only for HyP3-style interferogram zips, but these processors write **loose geocoded rasters** (ISCE3 `unwrapped/*.unw.tif`, GMTSAR `*_ll.grd`). `folder-ifg-list` now falls back to detecting those, and `render-tif` opens a loose file by path (required for the netCDF/GMT driver on `.grd`) instead of only reading from a zip.

- **GUI "Clear AOI" left result figures on the map** (`app/frontend/src/App.tsx`) — `handleClearAoi` cleared the AOI, footprints and results but not the rendered velocity/displacement/coherence overlay or its time-series marker/drawer. It now also clears `rasterOverlay`, `tsClickPoint` and `tsData`.

- **`insarhub analyzer … run --container --step …` errored with "argument --container: expected one argument"** (`cli/main.py`) — `--container` (with an optional value) was only registered on the parent analyzer parser, so placing it after the `run` action made argparse greedily consume the next token. It's now registered on the `run` subparser in its canonical after-the-action position (bare `--container` → default image).

- **GUI "Run in Container" no longer nests `docker run` inside the container (`docker: not found`)** (`processor/isce2_s1.py`, `processor/isce2_base.py`, `processor/isce3_base.py`, `app/routes/processor.py`) — ISCE2's `submit`/`retry` and ISCE3's `submit` guarded the container re-invocation only on `config.container` being set, not on `INSARHUB_CONTAINER_CHILD` (only GMTSAR did). So the container-side process, re-reading a persisted `container`, ran `docker run` **again inside the docker-less image**, giving `/bin/sh: docker: not found` (exit 127, misreported as a missing image). Added the `and not os.environ.get("INSARHUB_CONTAINER_CHILD")` guard to all of them, matching GMTSAR, so the container-side runs the stages locally. The CLI never hit this because it writes the run config *before* submit (so the reinvoke's container-stripped write lands last); the GUI route now does the same.

- **Container `ISCE2_S1` failed with `ModuleNotFoundError: No module named 'topsStack'`, then `'NoneType' has no attribute 'parent'`** (`docker/Dockerfile.isce2-mintpy`, `processor/isce2_base.py`) — in container mode `__init__` skipped ISCE2/topsStack discovery on **both** the host and the container side, but the container side is where the stages actually run and needs those paths. It now discovers on the container side (gated on `INSARHUB_CONTAINER_CHILD`), and the image puts topsStack (`share/isce2/topsStack`) on `PYTHONPATH` so `from topsStack.stackSentinel import …` resolves.

- **`refresh` reported "Run submit first" for the whole duration of a container run** (`processor/isce2_base.py`) — in container mode the step executor runs synchronously inside `submit()`, and the jobs file was only written *after* the entire loop, so mid-run there was no `isce_jobs.json` to read. The executor now persists the jobs file up front, before the loop; the per-step `.status` markers already update live.

- **`ISCE3_Dolphin_PL` now masks water out of the time-series inversion, matching native `dolphin run`** (`analyzer/dolphin_sbas.py`, `config/defaultconfig.py`) — dolphin's `displacement.run` passes the water mask to `timeseries.run` (`apply_mask_to_timeseries=True` → `mask_path=<water mask>`), so open water is excluded from the inversion. The analyzer, which reproduces that stage as a standalone `timeseries.run` call, was not passing `mask_path`, so it inverted water pixels too. A stage-by-stage comparison against a native `displacement.run` on the same geocoded CSLCs showed the two pipelines were byte-identical through `ifg`, `stitch`, and `unwrap`, and that the *only* divergence was in `sbas`: velocity/displacement matched exactly on all land pixels and differed **solely on water** (11,162 water pixels, 0 land pixels for the validation stack). Added an `apply_water_mask` config field (default **on**) that hands the processor's `dem/water_mask.tif` to `timeseries.run`; with it on, the analyzer's `velocity.tif` and cumulative-displacement rasters are byte-identical (`max|diff| = 0`, matching nodata pattern) to a native `dolphin run`. Turn it off to invert every pixel and keep open water in the outputs.

- **Single-frame S1_SLC jobs no longer get a `_merged_` folder name** (`app/routes/search.py`, `downloader/asf_base.py`, `downloader/s1_slc.py`) — selecting one frame created a `p<path>_merged_f<frame>` folder at add-job time while the subsequent download wrote a separate `p<path>_f<frame>`, so the stack file and the SLCs landed in different folders. Merge naming (`p<path>_merged_f...`) is now gated on **2+ frames sharing one path** across every code path that names a folder — the GUI's `add-merged-job` route, `download(merge=True)`, and `download_orbit(merge=True)` — matching `select_pairs()`, which was already gated. A single frame is therefore always `p<path>_f<frame>` in the GUI, CLI, and Python API alike; multiple frames still merge as before.

- **`max_workers` changes now take effect on an existing job folder** (`app/routes/folders.py`) — the web GUI's folder download read the download concurrency from the folder's saved `insarhub_config.json`, which froze `max_workers` at whatever it was when the folder was created; changing it in the settings form afterward had no effect (changing it *before* add-job did). Folder downloads now overlay the current form's execution settings (`max_workers`, `ssl_verify`) on top of the folder's saved search filters, so a GUI change applies to the next download.

- **`footprint()` crashed with `AttributeError: module 'matplotlib.cm' has no attribute 'get_cmap'`** (`downloader/asf_base.py`) — `matplotlib.cm.get_cmap` was deprecated in matplotlib 3.7 and removed in 3.9; with matplotlib 3.9+ the ASF search-result footprint map raised `AttributeError` the moment it tried to build its `hsv` colourmap. Replaced `plt.cm.get_cmap('hsv', N+1)` with `matplotlib.colormaps['hsv'].resampled(N+1)` (the registry API that works on 3.5+), which fixes the plot on any recent matplotlib.

- **`footprint()` basemap was blocked by OpenStreetMap's tile server ("Access blocked")** (`downloader/asf_base.py`) — the basemap was fetched from `tile.openstreetmap.org` without a User-Agent, which OSM's volunteer-run tile usage policy rejects outright (contextily/urllib sends the generic `python-requests` UA). `ctx.add_basemap` now passes `headers` identifying the app (`InSARHub/<version> (https://github.com/anomalyco/InSARHub)`), satisfying the policy's valid-User-Agent requirement.

### Changes

- **"View Data" moved from the Processor panel to the Downloader panel; the Processor viewer is now "View Result"** (`app/frontend/src/JobQueueDrawer.tsx`) — viewing raw downloaded scenes belongs with the downloader, and viewing processed interferograms with the processor. The Downloader's **View Data** shows raw-scene quicklooks; the Processor's **View Result** shows the geocoded interferograms it produced (see New Features).

- **Basemap: removed OpenStreetMap; light mode now defaults to Topo, dark to Satellite** (`app/frontend/src/{Map,MapToolbar,BasemapSwitcher,App}.tsx`, locales) — the OSM/Carto "Street" basemap was dropped, leaving **Satellite** (Esri imagery, suits the dark theme) and **Topo** (Esri World Topo, suits the light theme). The theme toggle re-defaults the basemap to the one that reads best for that theme.

- **`container` is now persisted to `insarhub_config.json`; `container_default` is never persisted** (`app/routes/processor.py`, `utils/config_io.py`, `utils/local_processor_reload.py`, `app/frontend/src/JobQueueDrawer.tsx`) — the image you actually chose is saved with the run config, so a later `refresh`/`retry` (and a GUI retry) re-runs inside the same image without re-passing `--container`. `container_default` (the fixed per-processor suggestion the GUI's "Run in Container" checkbox pre-fills) is stripped centrally in `write_insarhub_config`, so it no longer clutters the saved config or pins a stale default; the GUI reads it from the schema endpoint instead. An explicit `--container`/`container=` still overrides; a bare `--container` resolves to `container_default`.

- **Background-executor artifacts live under each processor's own directory** (`processor/isce2_base.py`, `processor/gmtsar_s1.py`, `processor/isce3_base.py`, `processor/isce3_nisar.py`, `processor/hyp3_base.py`, `config/paths.py`) — `executor.log`/`executor.pid` are written where the processor's other files go: `workdir/isce/` (ISCE2), `workdir/gmtsar/` (GMTSAR), and the workdir root (ISCE3, whose products already sit at the root). The filenames are shared constants (`EXECUTOR_LOG`/`EXECUTOR_PID`) and the paths are exposed per family in `config/paths.py`, which also gained a new **`ISCE3Paths`** dataclass and `executor_log`/`executor_pid` properties on `ISCEPaths`/`GMTSARPaths`; hardcoded path strings (`executor.log/pid`, `.stage_status`, `hpc`, `cropped_gslc`, `hyp3_jobs.json`) were replaced with these properties so no processor hardcodes them.

- **Analyzers renamed to reflect their inversion method** (`analyzer/*`, `config/defaultconfig.py`, routes, frontend, docs) — the MintPy `smallbaselineApp` analyzers are now suffixed `_SBAS` and the dolphin phase-linking analyzer `_PL`: `ISCE2_Mintpy_TS` → `ISCE2_Mintpy_SBAS`, `Hyp3_Mintpy_TS` → `Hyp3_Mintpy_SBAS`, `GMTSAR_Mintpy_TS` → `GMTSAR_Mintpy_SBAS`, `GMTSAR_TS` → `GMTSAR_SBAS`, and `ISCE3_Dolphin_TS` → `ISCE3_Dolphin_PL` (dolphin's estimator is always phase linking). Each config dataclass was renamed to match (e.g. `ISCE2_Mintpy_SBAS_Config`), and the module `analyzer/isce_sbas.py` → `analyzer/isce2_sbas.py`. The old registry names are kept as **aliases**, so existing `insarhub_config.json` files, saved jobs, and `-N <old name>` CLI calls continue to resolve unchanged.

- **`ASF_Base_Downloader.select_pairs()` now finalizes the stack and returns quality scores; new `quality_check`/`plot_network` flags** (`downloader/asf_base.py`, `utils/stack_io.py`, `cli/main.py`, `app/routes/folders.py`) — `select_pairs()` used to return only `(pairs, baselines, scene_bperp, prefetch_cache)` and left the whole "write stack files → seed weather/snow cache → precompute `PairQualityDB` → merge scores → plot network" sequence to its callers, so the CLI, the GUI and the Python API each re-implemented (and drifted on) that finalize step. The sequence is now shared in `utils/stack_io.finalize_stack()`, and `select_pairs()` runs it directly, gated by two new flags: `quality_check=True` (precompute coherence scores) and `plot_network=True` (save `network_*.png`). **Breaking**: it now returns a 6-tuple `(pairs, baselines, scene_bperp, prefetch_cache, quality_scores, quality_factors)` — `quality_scores`/`quality_factors` are `None` when `quality_check=False`. The CLI `--select-pairs` block collapses to a thin summary loop; the GUI passes `quality_check=False, plot_network=False` (it scores via its own async DB build). A `plot_pair_network()` call that doesn't pass `quality_scores` still renders the temporal-baseline legend — pass `quality_scores` (or just call `select_pairs()` with the defaults) for the pair-quality legend.

## [0.4.0] - 2026-08-13

### New Features

- **Processor (`GMTSAR_S1`)** — a new local/HPC processor running [GMTSAR](https://github.com/gmtsar/gmtsar)'s Python pipeline (`p2p_processing` for single-subswath, `p2p_S1_TOPS_Frame` for multi-subswath merged stacks) to generate Sentinel-1 interferograms from downloaded SLC `.SAFE` files. Supports `stack_mode` (align/topo/intf/merge stack stages), single- vs multi-subswath, HPC (SLURM) and `--container` execution. See [`docs/advanced/processor.md`](docs/advanced/processor.md#gmtsar_s1).

- **Processor (`ISCE3_Burst`)** — a new local/HPC processor building an interferogram stack from ASF `SLC-BURST` granules via [ISCE3](https://github.com/isce-framework/isce3)/[COMPASS](https://github.com/opera-adt/COMPASS) geocoding and [dolphin](https://github.com/opera-adt/dolphin) downstream. Coregistration-free by construction (each burst is geocoded onto absolute UTM). Stages: `dem`, `tec`, `cslc`, `static`, `crop`, `ifg`, `stitch`, `filt`, `unwrap`, `los`, with `phase_link` (default) and `network` interferogram estimators.

- **Analyzer (`GMTSAR_MINTPY_SBAS`)** — MintPy `smallbaselineApp` time-series on a `GMTSAR_S1` stack via GMTSAR's own `prep_gmtsar.py` loader; output → `workdir/gmtsar_mintpy/`.

- **Analyzer (`GMTSAR_SBAS`)** — GMTSAR-native SBAS inversion (`prep_sbas` + the `sbas` C binary), no MintPy; output → `workdir/gmtsar_sbas/`.

- **Analyzer (`Dolphin_SBAS`)** — dolphin `timeseries.run` inversion for `ISCE3_Burst` stacks (both `network` and `phase_link` estimators); output → `workdir/timeseries/`.

### Refactor (HPC job managers)

- **Every job manager is now sized identically and gets its partition's maximum walltime, with a new `"manager"` entry in `sbatch_options.json` for its partition** (`processor/_slurm_manager.py`, `processor/isce_base.py`, `processor/gmtsar_s1.py`) — a manager does no real work: it sits on a node running a bash poll loop that calls `sbatch`/`squeue` while its child jobs do the processing. Its walltime nonetheless has to outlive *every* child it supervises, since a manager expiring mid-run silently strands the remaining commands (and, with chained managers, every later stage too). That walltime was previously a per-step `manager_time` key read from `sbatch_options.json`, defaulting to a flat 24 h — both a value users had no good way to reason about, and a file that is otherwise entirely about the real processing work. Now:
  - Managers are fixed at **1 core / 1 GB** (was 1 core / 2 GB) — `MANAGER_CPUS_PER_TASK`/`MANAGER_MEM` in `_slurm_manager.py`, applied uniformly by all three manager builders (`build_sliding_window_manager`, plus `ISCE_Base`'s separate group-manager path, which had its own hand-rolled copy of the sizing).
  - Manager walltime is auto-detected as **the maximum its partition allows** (`manager_walltime()` → `sinfo -h -p <part> -o "%l"`, cached), e.g. `2-00:00:00` on this cluster's `all` or `30-00:00:00` on `smi_all`. Asking for the ceiling costs nothing (the manager holds one idle core) and is the only value that's both always-legal — SLURM rejects any `--time` above the partition's `MaxTime` — and never too short. Falls back to `1-00:00:00` when the limit can't be determined or the partition reports an unlimited one. The walltime parser handles SLURM's full format set, including the genuinely surprising rule that a bare number means *minutes* alone but *hours* after a `days-` prefix.
  - New `"manager": {"partition": "..."}` entry in both default templates: managers can be sent to a different partition than their children, which is worth doing where a long-walltime queue exists (they're idle babysitters that must outlive everything they supervise, so they suit a long/low-priority queue even when the real work belongs on a faster one). Only `partition` is read there — cores/memory/walltime stay fixed by design — and it also drives the auto-detected walltime, since the ceiling adopted is whichever partition the manager itself lands on.
  - `manager_time` is gone from `sbatch_options.json` entirely; that file now exclusively configures the child jobs (the real processors).

- **GMTSAR's MintPy SBAS `sbatch_options.json` step is keyed `"sbas"`, not ISCE's `"17"`** (`processor/gmtsar_s1.py`, `analyzer/mintpy_base.py`, `app/frontend/src/JobQueueDrawer.tsx`) — `Mintpy_SBAS_Base_Analyzer.submit_hpc()` is shared by `ISCE_SBAS`/`Hyp3_SBAS`/`GMTSAR_MINTPY_SBAS` and hardcoded step key `"17"` for all three. Those numbers are stackSentinel's own run-file indices (SBAS being ISCE's 17th and last step), so `"17"` is meaningful in an ISCE workdir but names nothing in a GMTSAR one, whose stages are `align`/`topo`/`intf`/`merge` — a borrowed label sitting incongruously among them. `submit_hpc()` now picks the key from the subclass's own `compatible_processor` (`GMTSAR_S1` → `"sbas"`, everything else → `"17"`, unchanged), and GMTSAR's default template carries a `"sbas"` entry in place of `"17"` with identical resources (it's the same MintPy `smallbaselineApp` workflow either way). The GUI's sbatch-options help text was also ISCE-specific for every processor — it described keys as "two-digit step number" and pointed at `"17"` even for a GMTSAR workdir; it now reads from the modal's existing `processorType` to name the right stage keys and SBAS key, and documents the new `"manager"` entry. Verified end-to-end: with children at `{cpus_per_task: 2, mem: 8G, time: 24:00:00, partition: all}`, the generated manager gets `1 core / 1G / 2-00:00:00 / all` by default and `1 core / 1G / 30-00:00:00 / smi_all` when `"manager": {"partition": "smi_all"}` is set, with child sizing untouched in both cases.

### Bug Fixes

- **Sliding-window HPC child jobs (ISCE_S1 and GMTSAR_S1 alike) silently fell back to `Slurmjob_Config`'s hardcoded `time=04:00:00`/`cpus_per_task=1`/`mem=4G` instead of their real per-stage `sbatch_options.json` values** (`processor/_slurm_manager.py`, `processor/gmtsar_s1.py`, `processor/isce_base.py`) — `build_sliding_window_manager()` took one `slurm_kwargs` dict and reused it both to build every child sbatch script *and* (via `**slurm_kwargs`) the lightweight manager script; passing a step's real resource sizing straight through would crash the manager with `TypeError: multiple values for keyword argument 'time'` (it already hardcodes `time=manager_time, cpus_per_task=1, mem="2G"` for itself), so both callers pre-stripped `time`/`cpus_per_task`/`mem`/`ntasks`/`nodes` out of the dict before calling — which fixed the manager but meant children never received those values either. Found while verifying a real `p100_f466_gmtsar` HPC retry requesting 24h walltime for slow `intf` pairs: the generated child `.sbatch` still showed `--time=04:00:00`. Fixed by splitting the concern inside `build_sliding_window_manager()` itself — it now takes the full per-stage `slurm_kwargs` for children as-is, and derives the manager's own (smaller) kwargs automatically by dropping the sizing fields, so callers no longer need to (and can't accidentally) starve children of their real resource allocation. `ISCE_Base._step_slurm_kwargs()` lost its now-dead `for_manager` parameter (always the child/full path now); `GMTSAR_S1._submit_stack_hpc()` updated to match. Verified via a synthetic test: child scripts now correctly carry `--time=24:00:00 --cpus-per-task=2 --mem=8G` while the manager itself still gets the lightweight `--cpus-per-task=1 --mem=2G`.

- **`GMTSAR_S1.refresh() --ls` showed a re-submitted pair as `FAILED` while it was actually `RUNNING`** (`processor/gmtsar_s1.py`'s `_print_table()`/`refresh()`) — per-command status checked the on-disk `cmd_XXXX.fail` marker before checking live `squeue` state; that marker is left over from the pair's previous, superseded attempt and only gets cleared (on success) or rewritten (on failure) once the *new* attempt itself finishes, so a currently-running retry still displayed the stale `FAILED` from before. Found immediately after retrying the 4 slow `intf` pairs from the walltime fix above — `squeue` showed them `R`(unning) while `refresh --ls` still said `FAILED (rc=unknown)`. Fixed by checking live `active_slurm`/queued state first, falling back to `.done`/`.fail` markers only when no current job id is live. Also fixed a related staleness source: per-command job ids were parsed from *every* historical `manager_<jobid>.out` log a stage's `.hpc/` dir has accumulated across retries, glob-ordered (i.e. arbitrary, not chronological) — an older retry's mapping could clobber the current one's for the same command index. Now sorted oldest-to-newest by job id (SLURM ids are monotonically increasing) before merging, so the current retry always wins. Verified live: after re-submitting 0022-0025, `refresh --ls intf` now correctly shows `RUNNING [job 504184]` etc., matching `squeue` exactly.

- **`GMTSAR_SBAS`: `-range` is now computed per scene instead of hardcoded, sbas flags match GMTSAR's recipe, and results are geocoded** (`analyzer/gmtsar_sbas.py`, `config/defaultconfig.py`) — checked the analyzer against §12 of "How to make an InSAR time series from Sentinel-1 TOPS data". The *workflow* already matched (`prep_sbas intf.in baseline_table.dat <path> unwrap.grd corr.grd`, then `sbas intf.tab scene.tab N S xdim ydim` with the echoed N/S/xdim/ydim parsed from prep_sbas's own output rather than re-derived by hand as the recipe instructs), but three things did not:
  - **`-range` was a hardcoded 866,000 m.** It is the radar-to-scene-centre distance and is frame-specific; the recipe computes it as `({[(c / rng_samp_rate) / 2] * ((x_min + x_max) / 2)} / 2) + near_range`, reading `rng_samp_rate`/`near_range` from the super-master PRM. New `_resolve_geometry()` does exactly that. Note the recipe's prose and its worked example disagree: written out it reads `({[(c/rng_samp_rate)/2] * ((x_min+x_max)/2)} / 2) + near_range`, but its own arithmetic multiplies by `x_max` and halves that rather than halving the midpoint again — taking the prose literally gives 873,283 m for its scene against the 901,085 m it states, 28 km low. The worked example is the physically sensible one (`slant-range-per-sample x midpoint-sample + near_range`) and is what's implemented. **`-incidence` is now computed too**, from the same PRM (`earth_radius`, `SC_height`) via the spherical-earth relation `cos(look) = (Rs^2 + R^2 - Re^2)/(2 Rs R)`, `sin(inc) = Rs sin(look)/Re`: on a real 3-subswath p100_f466 frame that is 39.53 deg at mid-swath, so sbas's built-in default of 37 is ~6% off on the DEM-error term while the recipe's hardcoded 40 is ~1% off. Validated independently by evaluating the same conversion at the merged grid's near and far edges — 30.49 and 45.98 deg, reproducing the published ~29.1-46.0 deg Sentinel-1 IW1-IW3 span. Both fall back to `config.range_dist`/`config.incidence` with a warning if the PRM can't be read.
  - **Flag defaults** now match the recipe's `-smooth 5.0 -rms -dem`: `smooth` 0 → **5.0**, `rms` False → **True**, `dem_err` False → **True**. `incidence` stays 37 (the recipe passes 40 but notes sbas's own default "is fine in most cases" and the value is "largely irrelevant"); `wavelength` was already the recipe's 0.0554658.
  - **Post-SBAS geocoding was missing entirely** (recipe §12c). `sbas` writes `vel.grd`/`disp_*.grd` in *radar* coordinates, so nothing could be mapped or compared against the geocoded MintPy path. New `geocode()` links `trans.dat` from the merge stage (relative symlink — it can exceed a gigabyte), runs `proj_ra2ll.csh` over `vel.grd` and every `disp_*.grd` to produce `*_ll.grd`, then builds `vel_ll.cpt` + `vel_ll.kml` via `grd2cpt`/`grd2kml.csh` as the recipe does. Called automatically at the end of `run()`, and non-fatal: the inversion has already succeeded and its radar grids are on disk by then, so a missing `trans.dat` warns rather than discarding the run. `GMTSAR_MINTPY_SBAS` is unaffected — it hands the merged stack to MintPy, which geocodes itself.

- **`GMTSAR_S1` unwrapping defaults aligned to GMTSAR's own recipe; the "landmask is broken" note corrected** (`config/defaultconfig.py`) — reviewed every unwrapping-related default against "How to make an InSAR time series from Sentinel-1 TOPS data" and followed it where it actually prescribes a value:
  - `near_interp` 0 → **1**. The recipe uses `snaphu_interp.csh` at every unwrapping step (`snaphu_interp.csh 0.01 40`, `0.001 40`), which fills low-coherence gaps before unwrapping, and GMTSAR's native `sbas` inversion wants every pixel valid. It had been 0 so GMTSAR interferograms matched ISCE topsStack's (which has no such step) for the three-backend comparison; the recipe takes precedence. On a multi-subswath stack this now only affects the single unwrap of the merged frame, since the per-subswath runs no longer unwrap at all. Flagged in the field comment: GMTSAR interferograms are now gap-interpolated where ISCE's are not — MintPy re-masks by coherence and inverts per-pixel so the effect is small, but not nothing.
  - `defomax` stays **0** — this was previously listed as a divergence, wrongly. The recipe's own text says "Maximum discontinuity threshold is usually set to zero for interseismic motion, where there are no large displacements. A number greater than zero will allow for phase jumps along discontinuities such as earthquake ruptures"; its examples use 40 only because the scene is the 2018 Kilauea eruption. For subsidence/interseismic work 0 *is* the prescribed value.
  - `threshold_snaphu` stays **0.1**, inside the recipe's own 0.001–0.10 range.
  - `mask_water` stays **0**, but its comment was materially wrong and is rewritten. It claimed GMTSAR's landmask is unusable; that finding was real but specific to `intf_tops.csh`, which derives the mask region from `gmt grdinfo phase.grd -I-` (with the `if (region_cut == "")` guard above it commented out, so it always overrides) at a point where the read can fail, leaving `landmask.csh` to run with an empty region and produce a `landmask_ra.grd` that corrupted snaphu's `phase_patch`. That call sits **inside** `intf_tops.csh`'s `if (threshold_snaphu != 0)` block, so with multi-subswath intf now passing 0 the fragile path is unreachable. The merge stage's landmask is a separate, sound implementation reading `gmt grdinfo phasefilt.grd -I-` — the same file the recipe has you read by hand — and honouring an explicit `region_cut`. Enabling `mask_water` is therefore safe again; it stays off by default only because the recipe conditions a landmask on "large areas of open water", where it also speeds unwrapping up.

- **`GMTSAR_S1` multi-subswath runs no longer unwrap and geocode each subswath separately — matching GMTSAR's own documented recipe** (`processor/gmtsar_s1.py`) — for a multi-subswath stack the per-subswath interferogram runs now get `threshold_snaphu = 0` and `threshold_geocode = 0`, so unwrapping and geocoding happen exactly once, on the merged full frame. This is what GMTSAR's own Sentinel-1 time-series recipe prescribes ("How to make an InSAR time series from Sentinel-1 TOPS data", §6b): *"The two zeros for threshold_snaphu and threshold_geocode indicate that we want to skip unwrapping and geocoding as this will be done after merging the subswaths."* Its table of contents makes the ordering explicit too — §7 *Merging Across Subswaths* precedes §8 *Unwrapping Interferograms*.

  The per-subswath unwraps were not merely redundant but entirely discarded: `merge_unwrap_geocode_tops.csh` consumes only `phasefilt.grd`, `corr.grd` and `mask.grd` from each subswath and never opens a per-subswath `unwrap.grd`. Measured on the real `p100_f466_gmtsar` stack (3 subswaths × 27 pairs), the intf stage burned **79.5 h of CPU across 81 child jobs** — median 8.5 min but mean 59 min and max 6.8 h, SNAPHU dominating — to produce output nothing downstream reads. Unwrapping is also the one step that cannot be parallelised away: GMTSAR calls SNAPHU single-threaded with full statistical-cost refinement (`INITONLY`/`NPROC`/`NTILEROW` are all left at their defaults in its shipped `snaphu.conf.brief`), unlike ISCE2, whose `runUnwrapMcf` defaults to `initOnly=True`.

  Implemented as a new `skip_unwrap_geocode` flag on `_config_with_stage()`, which already writes throwaway per-stage config copies — so no GMTSAR source is patched, and the shared `batch_tops.config` the merge stage reads is left untouched (verified: merge still sees `threshold_snaphu = 0.1` and unwraps the merged frame as before). Gated on `_multiswath`: a single-subswath stack has no merge stage, so it must still unwrap at intf, and its behaviour is unchanged. Safe because both gates in `intf_tops.csh` (unwrap at line 197, geocode at 237) sit *after* `filter.csh` (line 190), which is what actually produces the three grids merge needs. `product_dir()` already resolves to `merge/` for multi-subswath stacks, so both GMTSAR analyzers keep reading the merged, unwrapped product.

- **`GMTSAR_S1`'s `merge` stage now fans out one HPC job per pair, behind a new `mergeprep` seed stage** (`processor/gmtsar_s1.py`) — merge was a single job walking all 27 pairs serially (~2h40m on the real `p100_f466_gmtsar` stack: ~14 min for the first pair, ~5-6 min each for the rest). Each pair is genuinely independent — its own output directory, its own inputs — but `merge_batch.csh` computes the shared cross-pair geometry (`trans.dat`, 1.7 GB here, plus `raln.grd`/`ralt.grd`/`landmask_ra.grd`) inside whichever pair runs *first*, promotes it with `mv trans.dat ../`, and symlinks it into every later pair. That's the same shared-precompute-under-concurrency hazard as `intf_tops.csh`'s Stage 1, so it gets the same treatment as `topo`: a new `mergeprep` stage merges the seed pair alone to produce that geometry once, then `merge` fans the remaining pairs out as concurrent child jobs. Projected ~2h40m → ~26 min at 18 workers.

  The per-pair work is a Python port of `merge_batch.csh`'s loop body rather than a call into it, because the csh **structurally cannot process an arbitrary pair in isolation**: it builds its supermaster PRM reference from *line 1* of its input file (`awk 'NR==1' ... > tmpm.filelist`) while taking each pair's own reference from the line currently being processed. Those are different fields of different lines, so a single-line input collapses them — every pair after the first would silently be merged against *its own* reference instead of the stack's supermaster, giving each merged pair a different radar-grid origin and quietly corrupting the time series. (Passing a two-line file instead makes every child job reprocess the supermaster pair, racing on its shared output directory.) The seed pair is the one case where the two coincide, so `mergeprep` uses the stock csh unchanged. Verified by merging an already-serially-merged pair through the new path in a sibling directory at identical depth and comparing with `grdinfo -C`: all 8 products (`unwrap`/`corr`/`phasefilt`/`los_ll`/`unwrap_ll`/`unwrap_mask`/`mask`/`conncomp`) identical in every field. Also found while verifying that `merge_unwrap_geocode_tops.csh` exits 1 on a trailing `rm` over an empty glob ("rm: No match.") even on success — invisible via `merge_batch` because a csh `foreach` body doesn't propagate it, but fatal when invoking the script directly — so per-pair success is judged by the product existing, not the exit code. Already-merged pairs are skipped, so a retry resumes rather than restarts.

- **`GMTSAR_S1`'s multi-subswath `merge` stage always failed: `dem.grd` was never staged into `merge/`** (`processor/gmtsar_s1.py`) — `merge_batch.csh` checks for `dem.grd` in its own working directory before doing anything else (`if (! -f dem.grd) then; echo "dem.grd is required ..."; exit 1`) and later symlinks it into each per-pair subdir it creates (`ln -s ../dem.grd .`), so the file has to sit at `merge/dem.grd` specifically. `_stage_stack()` only ever puts the DEM in each subswath's own `topo/` dir, and `_run_merge_unit()` wrote `intflist`/`merge_input` into `merge/` without it — so the merge stage died 3 seconds in with `produced 0/27 merged pairs`, *after* every align/topo/intf pair had already succeeded (i.e. after the entire expensive part of a full-frame run). Found on the real `p100_f466_gmtsar` stack, whose 27 pairs × 3 subswaths all completed before merge failed. Fixed by symlinking any subswath's `topo/dem.grd` (it's one downloaded DEM staged per swath, identical across them) to `merge/dem.grd` before invoking `merge_batch` — a symlink rather than a copy, matching what GMTSAR's own usage text asks for ("Also make sure the dem.grd is linked"). Verified end-to-end: the retried merge now finds the DEM and produces per-pair merged directories.

- **A global `logging.disable(logging.CRITICAL)` was swallowing every log message in the entire codebase** (`insarhub/__init__.py`, `cli/main.py`) — line 14 of the package's own `__init__.py` called `logging.disable(logging.CRITICAL)` at import time. That is a process-global kill switch: it isn't scoped to InSARHub's loggers, isn't undoable by a caller's own logging setup, and silences *everything* at CRITICAL and below — so all 41 `logger.info(...)` progress messages plus every `logger.warning`/`logger.error` across processors, analyzers and utils were discarded before reaching a handler, in the CLI and in any host application that imported insarhub. Whole commands consequently looked like no-ops: `processor -N GMTSAR_S1 ... cancel` scancelled every job and printed nothing at all (the symptom that surfaced this), and `retry` resubmitted a stage just as silently. Removed, with a comment recording why it must not come back. Verified it was buying nothing: with it gone, importing `insarhub` and every heavy submodule emits no log records at all even at DEBUG — the one visible import-time line (pyproj's "unable to set PROJ database path") comes from the `warnings` module, which `logging.disable()` never affected anyway. Separately, nothing in the package ever installed a logging handler either, so `logger.info` would still have gone nowhere: `cli/main.py`'s `main()` now configures levels once at the entry point (root at WARNING so third-party libraries stay quiet, `insarhub`'s own loggers at INFO), via `basicConfig`, which is a no-op when a handler already exists so an embedding application's setup still wins.

- **`GMTSAR_S1`'s `submit`/`retry` output now matches `ISCE_S1`'s, and `retry` no longer resubmits already-finished stages** (`processor/gmtsar_s1.py`) — both reported through `logger` in a terse one-line-per-event style while `ISCE_Base` prints a structured, coloured breakdown, so the same workflow read completely differently depending on the processor. `_submit_stack_hpc()` now emits ISCE's exact shape: a `✓ <stage>  (all commands already done)` line per skipped stage, `All stages already complete.` when there's nothing to do, a `▶ [<stage>]  →  manager [<jobid>]  (N cmd, N batch(es), max N concurrent)` line per stage built (with `(chained, queued after previous stage)` for the non-first ones), and the closing `First job queued [<id>] — N stage(s) total, chaining automatically. SSH session can now be closed — use 'refresh' to check status.` `retry()` gained ISCE's `No failed stages.` / `Retrying N stage(s) from <stage>…` messages (plus `No failed pairs.` / `Retrying N pair(s)…` in per-pair mode, which had no retry message at all).

  Behaviour change while aligning the retry semantics: `retry()` reset **every** stage to PENDING, so a failure in `intf` resubmitted the already-succeeded `align` and `topo` managers too, purely to have them skip every command via their `.done` markers — two extra queued manager jobs and a stretch of misleading `RUNNING` status for work that was already finished. It now resets only from the first failed stage onward, exactly as `ISCE_Base.retry()` does; earlier stages keep their SUCCEEDED marker and are skipped by `_submit_stack_hpc()`'s existing pass-1 check. Verified on a synthetic workdir: with `align`/`topo` SUCCEEDED and `intf` FAILED, retry reports `Retrying 2 stage(s) from intf…` and leaves both earlier markers untouched.

- **`GMTSAR_S1.cancel()`'s output now matches `ISCE_S1`'s** (`processor/gmtsar_s1.py`) — it reported through `logger`, while `ISCE_Base.cancel()` uses coloured `print()`, so the two processors' cancel commands read differently even before the logging bug above made GMTSAR's output vanish entirely. GMTSAR now uses the same coloured `print()` calls with identical wording ("No SLURM job IDs found.", "scancel: cancelled N job(s).", "scancel error: …", "Sent SIGTERM to executor (PID N).", "Process already finished.", "Cancel error: …"), and the two-phase manager/child cancellation reports one combined total rather than a line per phase, matching ISCE's single summary line. The count now reflects jobs that were genuinely still active (checked against `squeue` before cancelling) rather than the number of ids tried, since the id lists deliberately include already-finished jobs from earlier runs.

- **`GMTSAR_S1.cancel()` could leave orphaned child jobs running after their manager was killed** (`processor/gmtsar_s1.py`) — it read every stage's `submitted_child_jobs.txt` up front and then issued one combined `scancel` for managers and children together. But a running sliding-window manager keeps submitting new children as slots free up, so anything it submitted between that read and `scancel` landing survived, with its manager already dead and nothing left to reap it. Now two-phase: managers are cancelled first (stopping new submissions at the source), then after a short settle the child list is re-read — now final — and cancelled. Re-cancelling an already-finished id in the overlap is free: verified `scancel` exits 0 for both completed and entirely-unknown job ids, so neither stale `chained_job_id.txt` entries from previous runs nor the phase overlap produce spurious "scancel error" logs. Also verified against a live 19-job run that the id collection covers every running manager and child exactly.

### Features

- **`ISCE3_Burst` is complete end to end: the interferogram stack now runs on `dolphin` rather than the COMPASS workshop notebook's `utils.py`** (new `processor/_isce3_dolphin.py`, `processor/isce3_burst.py`, `config/defaultconfig.py`) — the processor previously stopped at `cslc`, where COMPASS itself stops. Everything after that (pairing, interferogram formation, stitching, multilooking, filtering, coherence, unwrapping) existed only as hand-rolled helpers in the tutorial's `utils.py`. Each has a maintained equivalent in [dolphin](https://github.com/opera-adt/dolphin), the OPERA package behind the operational DISP-S1 product, so those are called instead of vendoring a copy that would drift:

  | notebook `utils.py` | dolphin |
  |---|---|
  | `generate_ifgram_pairs` | `interferogram.Network(max_bandwidth=…)` |
  | `form_single_ifgram` | `interferogram.VRTInterferogram` |
  | `stitch_ifgrams` | *(hand-written — see below)* |
  | `multilook_tif` | `utils.take_looks` |
  | `filter_tif` | `goldstein.goldstein` |
  | `generate_phsig_coh_tif` | `interferogram.estimate_interferometric_correlations` |
  | `unwrap_single_ifgram` | `unwrap.run` (snaphu-py) |

  Five new stages — `crop`, `ifg`, `stitch`, `filt`, `unwrap` — leaving `static` as the only unimplemented one. The output is a stack of unwrapped interferograms plus connected-component labels, which is what SBAS consumes.

  `Network(max_bandwidth=N)` is the exact analogue of the notebook's `n_connections=N` (both connect each acquisition to its next *N* neighbours by index), so `n_connections` maps straight through and the network is unchanged. Verified against the notebook's own `ifgram_list.txt` on the 9-date Hawaii A124 stack: 21 pairs, identical set. Stage boundaries differ in one place — the notebook's sections 3.5/3.6/3.7 (multilook, filter, coherence) are a single `filt` stage here, because keeping them separate means writing and re-reading full-size complex rasters twice for no benefit.

  Stitching is the one step that could **not** be delegated. `dolphin.stitching.merge_images` mosaics by warping through GDAL, and a burst's empty region in these interferograms is plain `0+0j` rather than a declared nodata value — so the last file's zeros overwrite every earlier file's real data. Declaring `nodata=0` on the rasters and passing `in_nodata=0` were both measured to change nothing: GDAL does not honour nodata for complex bands. On the Hawaii A124 stack that silently turned a 1103 km² two-burst union into 583 km² — exactly one burst's worth, with no warning and no error. It reproduces on the notebook's own per-burst files, so it is not an artefact of how the crops are cut. dolphin is not at fault for its own purpose: DISP-S1 stitches unwrapped and phase-linked rasters, which are real-valued and carry proper nodata; complex burst mosaicking is simply outside its remit. New `_mosaic_complex()` composites by explicit validity mask (`|z| > 1e-6`), keeping the first valid pixel — and pastes by integer offset rather than resampling, since all bursts already share the CSLC grid and interpolating across a burst edge would smear the phase discontinuity there. Verified against an independently computed union of the two burst masks: 1101 km² against 1103 km² expected, the 0.2% being edge rounding.

  Four things had to be handled that the notebook's helpers hid:
  - **The water mask is not a raster.** `swbd_nasadem.wbd` is a headerless uint8 array whose geotransform lives in a sidecar `.json`; GDAL cannot open it at all, so passing it to dolphin's `mask_filename` fails with *"not recognized as being in a supported file format"*. New `water_mask_on_grid()` reads it with numpy, wraps it in an in-memory GDAL dataset and warps it onto the stack's grid. It also **inverts** it: the `.wbd` marks water with nonzero, while dolphin's convention is `1 = valid, 0 = invalid`. That inversion is the dangerous half — getting it backwards raises nothing and simply unwraps the ocean while masking the land.
  - **The crop window must be intersected with the burst's own extent.** A burst is a slanted footprint inside a much larger bounding raster, and an AOI commonly reaches past its edge. `gdal.Translate` honours a `projWin` beyond the source and pads the difference with nodata rather than clipping, so the first cut carried ~17 km of empty easting and ~10 km of empty northing into every downstream raster. `_intersect_window()` clips the window to the source extent first; the cropped rasters went from 6879×1982 to 5188×1490 with the same valid pixels.
  - **Multilooking must move the geotransform.** `take_looks` returns a bare array; writing it back with the source geotransform georeferences every downstream product wrong by the look factors. The pixel sizes are scaled explicitly.
  - **`PROJ_DATA`/`GDAL_DATA` must be set explicitly.** conda sets these from `activate.d` hooks, which never fire for a bare `<env>/bin/python` — how SLURM child jobs and non-activated subprocesses run. pyproj carries its own fallback and keeps working, so the failure surfaces only later, inside GDAL at raster-write time, as an unrelated-looking `PROJ: proj_create_from_database … failed`. New `ensure_proj_env()` sets them from the running interpreter's prefix.

  New config fields: `max_temporal_baseline` (pair by days instead of neighbour count), `crop_buffer_deg`, `coh_window`, `unwrap_nlooks`, `unwrap_tiles`, `unwrap_cost`, `unwrap_init_method`. Note that coherence is estimated *after* Goldstein filtering, following the notebook — it is therefore a filtered-phase quality measure comparable to ISCE's `filt_fine.cor`, not a raw normalised cross-correlation, and is documented as such so it isn't read as the latter.

- **`ISCE3_Burst`'s `cslc` stage is judged on its products, not the run script's exit code** (`processor/isce3_burst.py`) — COMPASS writes each CSLC `.h5` and only then renders a PNG browse image, a step that needs GDAL's HDF5 driver. On an installation without `libgdal-hdf5`/`libgdal-netcdf`, every run script exits non-zero *after* having written a complete, correct product, so the whole stage reported `FAILED` with all 18 CSLCs on disk and byte-identical to the notebook's. The stage now requires every expected `.h5` to exist and logs the non-zero exits as a warning rather than letting them veto a complete result.

- **`GMTSAR_S1`: auto-detect `gmtsar_root`/`gmtsar_env_bin`, `--container` support** (`processor/gmtsar_s1.py`, `config/defaultconfig.py`) — both fields were previously required with no fallback, raising immediately at construction if unset. HPC mode is handled differently: the outer `submit()`/`_submit_stack_hpc()` call is pure sbatch-script bookkeeping that never touches GMTSAR/`gmt` itself, so it deliberately stays on the host regardless of `container` (re-invoking it would also be a no-op, since `container` isn't persisted to `insarhub_config.json`); instead each HPC child job's own `run-stage-unit` command gets wrapped via `wrap_container_cmd()` in `_stage_commands()`, since that's the thing that actually needs GMTSAR. `cancel()` extended to also `SIGTERM` a containerized local-mode run's real host-side PID (written by `_reinvoke_via_container` to `case_dir/executor.pid`) — previously documented as "nothing to cancel" for local mode, which is only still true for the plain non-container daemon-thread case.

  Also fixed along the way: `retry()` never checked `hpc_mode` at all for `stack_mode`, always falling back to a local daemon thread even for a stack originally submitted with `--hpc-mode` — now delegates to `_submit_stack_hpc()` correctly, matching `submit()`'s own branching.

Bash `write_status()` is supplied per-caller now (extracted alongside the rest of the sliding-window manager machinery into the new shared `_slurm_manager.py`, see the Refactor entry above): `ISCE_S1` writes a single status text file, `GMTSAR_S1` touches/removes `.succeeded`/`.failed` marker files in `.stack_status/<stage>/`, matching `_read_status()`'s existing on-disk convention exactly.

Applies to both the per-pair and stack_mode paths.

(Stack mode also now bumps `threshold_snaphu` off 0 with a warning, since SBAS requires unwrapped interferograms.)
- **GMTSAR time-series (SBAS) support** (`processor/gmtsar_s1.py`, `config/defaultconfig.py`, new `analyzer/gmtsar_sbas.py` + `analyzer/gmtsar_mintpy_sbas.py`) — `GMTSAR_S1` gained a `stack_mode` flag that produces a coherent time-series stack instead of independent per-pair interferograms: it aligns the whole scene set to one shared super-master and batch-generates interferograms across the downloader-selected pair network, yielding a single `baseline_table.dat` spanning every date. ### Bug Fixes

- **`GMTSAR_S1` was unusable through the web GUI** (`app/routes/processor.py`, `app/state.py`, `app/frontend/src/JobQueueDrawer.tsx`, new `core/local_processor_reload.py`) — the GUI's processor routes independently reimplemented (in an ISCE_S1-only shape) logic the CLI had already generalized for GMTSAR_S1: `_run_folder_process` never converted `stack_p*_f*.json`'s bare-scene-name pairs into GMTSAR_S1's required 4-tuples; `processor.submit(steps=...)` was called unconditionally even though `GMTSAR_S1.submit()` takes no `steps` argument; `get_folder_local_jobs` hardcoded `isce_jobs*.json`/`workdir/isce/`, never finding `workdir/gmtsar/gmtsar_jobs.json`; `_run_local_action` constructed configs with a `saved_job_path` field `GMTSAR_S1_Config` doesn't have and reconstructed pairs assuming ISCE's step-keyed job shape (`KeyError` on GMTSAR_S1's real `{"pair": [...]}` shape); `cancel` crashed with `AttributeError` (`GMTSAR_S1` has no `cancel()`); and the frontend's `JobQueueDrawer.tsx` hardcoded `processorType === 'ISCE_S1'` to decide local-vs-cloud job UI, routing `GMTSAR_S1` through the Hyp3 cloud-job endpoints entirely. Fixed by extracting the CLI's already-correct job-file-discovery/saved-processor-reload helpers (`_jobs_glob`, `_find_jobs_file`, `_load_local_processor`, etc.) into a new shared `core/local_processor_reload.py` both the CLI and the web routes now import from, fixing all of the above in one pass instead of two independent (and now identically correct) implementations. `app/state.py`'s processor metadata now exposes an `is_local` flag (same `"pairs" in signature` check `_run_folder_process` already used) so the frontend derives local-vs-cloud generically instead of hardcoding a processor name.
- **`GMTSAR_S1`'s output subfolder renamed `gmtsar_case/` → `gmtsar/`** (`processor/gmtsar_s1.py`) — matches the sibling naming convention already used by every other processor/analyzer under a stack's workdir (`isce/`, `hyp3/`, `mintpy/`). Breaking for any existing workdir with real output already under `gmtsar_case/` — rename that directory to `gmtsar/` manually to keep using it with the updated code (or the CLI/`GMTSAR_S1` won't find its saved `gmtsar_jobs.json`).
- **`GMTSAR_S1` couldn't consume `insarhub downloader --select-pairs` output at all** (`processor/gmtsar_s1.py`, `cli/main.py`) — the downloader's own pair-selection output (`stack_p<path>_f<frame>.json`) stores pairs as 2-tuples of bare ASF scene names, with no `.SAFE` suffix and no `.EOF` orbit filename, while `GMTSAR_S1.__init__` requires 4-tuples `(ref_safe, ref_eof, sec_safe, sec_eof)` and rejects anything else — so feeding real downloader output straight into `GMTSAR_S1` crashed immediately on construction. Separately, real downloader output stores SLCs as `.zip` (never auto-extracted), while GMTSAR needs an already-extracted `.SAFE` directory in both `frame_mode` settings. New `pairs_from_downloader()` (`gmtsar_s1.py`) converts a downloader `stack_p*_f*.json` (or an already-loaded flat pairs list) into GMTSAR_S1's required 4-tuples, resolving each scene's `.EOF` local-first (scans `orbit_dir` for a file whose own validity window covers the scene, matching real downloader output where `.EOF` files are already staged alongside the SLCs) and falling back to the existing `_ensure_poeorb()` POEORB-cache lookup (`utils/tool.py`) only if nothing local covers it. New `GMTSAR_S1._ensure_safe_extracted()` auto-extracts a scene's `.zip` into a real `.SAFE` directory the first time it's needed, called once per unique scene at the start of `_stage_case()`. `cli/main.py`'s pairs-loading dispatch now detects 2-tuple pairs for `GMTSAR_S1` specifically and routes them through `pairs_from_downloader()` before construction; already-correct 4-tuples (e.g. a hand-built `--pairs-file`) pass through unchanged.
- **`ISCE_S1` DEM auto-download preferred the search AOI over the actual SLC footprint** (`processor/isce_s1.py`, `config/defaultconfig.py`) — `_prepare_dem()` used `config.bbox` directly whenever it was set, only falling back to deriving a bbox from the real SLC manifests on disk (`_bbox_from_slc_dir()`) if `bbox` was unset. But the search AOI only reflects what was searched for — ASF returns whole-scene footprints that extend beyond it, and for a merged multi-frame stack (`--merge`) the true combined footprint of every constituent frame can differ substantially from whatever AOI was used to find them. Fixed: the joint footprint of the actual SLCs found in `slc_dir`/`workdir` is now tried first regardless of whether `bbox` is set, so the downloaded DEM always covers every frame actually being processed; `bbox` is used only as a fallback when no SLCs are on disk yet to derive a footprint from (e.g. a dry run before download).
- **`Hyp3_SBAS` and `ISCE_SBAS` silently share/overwrite the same `mintpy/` directory when pointed at the same workdir** (`test/e2e/cli_e2e_isce_mintpy.sh`, `test/e2e/api_e2e_isce_mintpy.py`) — `MintPyPaths.mintpy_dir` (`config/paths.py`) is `workdir / "mintpy"` with no analyzer-type awareness, so both analyzers derive the identical output directory when run against the same workdir — `ifgramStack.h5` (same filename either way, despite very different content: HyP3's geocoded 3661×2899 vs ISCE's radar-coordinate 3437×3281), `smallbaselineApp.cfg`, `velocity.h5`, `timeseries.h5`, `pic/`, etc. all silently collide, with whichever pipeline ran most recently overwriting the other's results with no error or warning. `cli_e2e_hyp3_mintpy.sh` and `cli_e2e_isce_mintpy.sh` (plus their API equivalents) both defaulted to the same `p100_f466/` workdir, hitting exactly this — likely the real explanation for a confusing, hard-to-reproduce `'STARTING_RANGE'` `KeyError` seen partway through this investigation. Fixed the e2e tests by giving the ISCE variant its own default workdir (`p100_f466_isce/`). The underlying core issue (no analyzer-type separation in `MintPyPaths`) remains for any real user who processes the same AOI with both `Hyp3_SBAS` and `ISCE_SBAS` against one workdir — deliberately not changed here, pending a decision on the right fix (e.g. `workdir/mintpy_hyp3/` vs `workdir/mintpy_isce/`).
- **A clip raster left behind by an interrupted `Hyp3_SBAS.prep_data()` run was silently skipped forever on every subsequent rerun** (`analyzer/hyp3_sbas.py`) — `_clip_rasters()`'s skip-existing check was a bare `if out.exists(): continue`, with no validation that the file was actually a complete, valid raster. If a prior clip write was ever interrupted (crash, Ctrl+C, disk full, an earlier bug elsewhere in the process) it left a corrupt/truncated file sitting at the final output path; every later `prep_data()` rerun then saw "it exists" and skipped regenerating it, so the corrupt file (which GDAL/MintPy's `prep_hyp3.py` would reject with `ERROR 4: ... not recognized as being in a supported file format`, then crash with `'NoneType' object has no attribute 'RasterXSize'`) persisted indefinitely. - **HyP3 `watch` deadlocked the moment any job succeeded — download never started** (`cli/main.py`) — `_proc_watch()` called `processor.download()` from *inside* a `with tqdm.external_write_mode(...)` block. `external_write_mode()` acquires tqdm's process-global write lock for its entire `with` body; `download()` spawns a `ThreadPoolExecutor` whose worker threads each open their own per-file `tqdm` progress bar, which also needs that same global lock to initialize/update. Result: the main thread holds the lock waiting for the download workers to finish, while every worker blocks trying to acquire that same lock just to report progress — a guaranteed deadlock on the very first successful job, confirmed live via `ss -tnp` (real response bytes queued unread in the kernel socket buffer while every thread sat in `futex_do_wait`). ## [0.1.0] - 2026-03-06

### Initial Release

First public release of **InSARHub** — a modular Python framework for automated InSAR time-series processing.

---

### Features

#### Downloader
- `ASF_Base_Downloader`: Search and download Sentinel-1, ALOS, and NISAR SLC data via the ASF Search API
- Spatial filtering with bounding box, WKT, or GeoJSON/shapefile AOI
- Post-search filtering by date range, path/frame, flight direction, polarization, season, coverage, and scene count
- Scene footprint visualization with basemap overlay (`footprint()`)
- DEM download via `dem-stitcher` aligned to search footprints
- Multi-threaded download with Ctrl+C cancellation and partial-file cleanup
- `S1_SLC`: Sentinel-1 SLC specialized downloader with orbit file (`sentineleof`) support

#### Processor
- `Hyp3_S1`: Submit, monitor, download, retry, and persist HyP3 InSAR jobs
- Multi-account credential pool with automatic credit-aware job rotation
- Batch job persistence (save/load JSON) for resumable workflows
- `watch()` mode: polls job status and downloads succeeded outputs continuously
- Retry failed jobs with automatic timestamp-stamped save files

#### Analyzer
- `Hyp3_SBAS`: End-to-end MintPy SBAS time-series analysis from HyP3 outputs
- Automatic unzip, file collection, common-overlap clipping, and MintPy config generation
- Optional pyAPS tropospheric correction with CDS API credential management
- `cleanup()` to remove temporary files after processing

#### Utilities
- `select_pairs`: Temporal and perpendicular baseline filtering with configurable targets and tolerances
- Local baseline computation (zero network calls for Sentinel-1 and ALOS)
- API fallback with threaded fetching for products without local baseline data
- Connectivity enforcement: minimum/maximum degree per scene with force-connect option
- `plot_pair_network`: Network visualization with per-scene connection histogram
- `ERA5Downloader`: Batch ERA5 reanalysis download for MintPy tropospheric correction, MintPy-compatible filenames
- `clip_hyp3_insar`: Clip HyP3 zip outputs to a custom AOI before analysis
- `Slurmjob_Config`: Generate SLURM batch scripts for HPC job submission
- `earth_credit_pool`: Load multi-account Earthdata credentials from a pool file

#### CLI (`insarhub`)
- `insarhub download` — search, filter, and download SLC scenes
- `insarhub processor submit/refresh/download/retry/watch/save/credits` — full HyP3 job lifecycle
- `insarhub analyzer prep/run` — prepare and run MintPy analysis
- `insarhub utils select-pairs/plot-network/era5/clip` — utility commands
- Workdir (`-w`) and credential pool (`--credential-pool`) flags across all subcommands

#### Core
- Auto-registering component registry (`Downloader`, `Processor`, `Analyzer`)
- `InSAREngine`: high-level pipeline runner with skip flags and watch mode
- Unified `CommandResult` pattern shared between CLI and Panel frontend
